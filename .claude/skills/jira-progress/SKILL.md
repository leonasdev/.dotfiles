# Jira 進度更新 Comment 產生器

你的任務是將這次 session 的工作內容，整理成一段可以直接貼到 Jira ticket comment 的進度更新。

## 核心原則

這份進度報告的讀者不只是工程師，還包括 PM 和主管。寫的時候請站在「使用者要在會議上用這份內容報告進度」的角度思考：

- **用中文撰寫**
- **產出的格式是 Jira wiki markup**，放在 codeblock 中讓使用者可以直接複製
- **要能展現工作的實質內容與複雜度**：讓讀者感受到這項工作涉及哪些面向、需要處理哪些考量。寫得太草率（例如「修好了一個 bug」）會讓人誤以為任務很簡單、不花時間。但要注意，份量是靠「講出關鍵的判斷、數據與取捨」展現的，不是靠字多。一段話寫得長不代表讀者感受到的份量就重，往往只是讀不下去
- **使用者要能對每一點口頭說明**：不要放進只有你在執行過程中才知道、使用者被追問時答不出來的細節（具體的除錯步驟、實作層級的程式碼改動）

## 讓證據說話，而不是用散文描述證據

這是這份 skill 最重要的一點。過去產出的 comment 最大的問題是：**從頭到尾都是同一種質地的文字**，讀者必須逐字讀完整段散文，才能拼湊出「所以結果到底是什麼」。

正確的作法是：**只要用具體形態呈現會比文字更好懂，就直接呈現它本身，不要用散文轉述。** 散文則專心負責讀者無法從證據自己看出來的那部分，也就是「為什麼」。

這不只是為了讓 comment 變短，而是因為證據本身比轉述更可信、更快掃讀，而且在會議上被追問時，使用者可以直接指著那個表格或那行輸出回答。

### 對照

散文轉述（原本的寫法）：

```
* 執行 5 分鐘的 fuzzing 測試，libaflgo 版本找到 429 個 crash，原版找到 0 個
* 差異原因是 libaflgo 額外啟用了 CmpLog（一種能幫助 fuzzer 更有效突破比較條件的
  機制），大幅提升了觸發 crash 的能力
```

證據呈現（要改成的寫法）：

```
||版本||5 分鐘 crash 數||CmpLog||
|libaflgo|429|有|
|原版 selectfuzz|0|無|

差異來自 {{CmpLog}}（幫 fuzzer 突破 magic number 這類比較條件的機制），原版基於較舊的 AFL 因此沒有這個功能。
```

第二種寫法更短，但資訊量更大：數字對齊了、變因（CmpLog 的有無）一眼可見，而散文省下來的空間拿去補「為什麼原版沒有 CmpLog」這個讀者真正會問的問題。

### 可以拿來當證據的素材

在動筆前，先掃過這次 session，問自己「有沒有現成的東西可以直接貼」：

- **表格**：任何 A/B 比對、前後對照、多個項目各有幾個數值。Jira 表格的標題列是每格用兩個直線包住，資料列用一個直線分隔，見下方語法區的範例
- **實際輸出片段**：錯誤訊息、警告、測試結果、指令輸出。用 `{noformat}` 包住
- **指令 + 結果**：說明「怎麼驗證的」時，貼出實際跑的指令最有說服力。用 `{code:bash}`
- **程式碼 / 設定片段**：關鍵的設定值、關鍵的幾行改動。用 `{code:c}`、`{code:python}` 等
- **狀態標記**：多項工作各自的完成狀態，用 `(/)` 完成、`(x)` 失敗、`(!)` 待處理。這些在 Jira 上會渲染成對應的圖示

### 什麼時候該用，什麼時候不該用

判準只有一個：**這樣呈現會不會比純文字更好懂。** 會，就用；不會，就老實寫文字。

- 一組數字要互相比對 → 表格。讀者掃一眼就看到差在哪，換成句子反而要在腦中重建對齊關係
- 「這個 counter 的累加不是 atomic」這種事 → 直接貼那一行 `counter += 1`。看到那行比讀三句解釋更直觀，這就是程式碼該出現的時候
- 錯誤訊息、警告的實際長相 → 貼原文。轉述成「出現了找不到 target 的警告」不如讓讀者直接看到那行字
- 純粹的判斷、取捨、風險評估 → 用文字。這些東西本來就沒有對應的形體，硬塞程式碼或表格只會讓讀者更難抓到重點

不要為了「版面上要有東西」而去湊。也絕對不要編造輸出、數字或程式碼，寧可用文字誠實描述。

### 證據是用來「取代」散文，不是疊在散文上

這是最容易做錯的一步。加了表格或程式碼之後，**回頭把原本用文字描述同一件事的句子刪掉**，只留下讀者從證據看不出來的那部分（通常就是「為什麼」）。

如果一段內容表格也有、散文也有，那不但沒有變好懂，還比原本更長更難讀，等於白做。判斷方式很簡單：讀者看完這個表格之後，下面這句話還有沒有告訴他新的東西？沒有就刪掉。

### 貼程式碼與輸出的分寸

- **裁切到承載重點的那一到三行**。一段 40 行的 log 或一整個函式貼進 comment 只會讓人整段跳過，而且重點會被淹沒。挑出決定性的那幾行，其餘用 `...` 省略
- **旁邊的說明要用使用者講得出口的語言**。可以貼 `counter += 1` 並說明「這是 read-modify-write，兩個 process 同時做會互相覆蓋」；不要貼一整段夾雜著跟重點無關的 flag 運算、memcpy、barrier 的程式碼，然後期待使用者在會議上解釋得出來
- **不要用表格列檔名和函式名**。那種表格對理解沒有任何幫助，只是把散文換個排版，還會讓讀者以為需要記住這些名字

### 截圖

你無法把圖片附進 comment（使用者會自己貼到 Jira），所以**不要**在 comment 內容裡放 `!image.png!` 這類佔位語法，那會讓使用者貼上去之後出現破圖。

如果某個段落用截圖呈現會明顯比文字好（例如 fuzzer 的統計畫面、UI 變更、監控圖表、工具的視覺化輸出），在**輸出的 codeblock 外面**用一兩句話提醒使用者，指明建議貼在哪一段下方、以及那張圖要呈現什麼。只在真的有幫助時提，沒有就不要提。

## 撰寫要領

每一項工作描述都要讓讀者理解因果脈絡，而不只是列出結論。在證據已經呈現「發生了什麼」之後，文字的職責就集中在「為什麼」。

- **不要用空泛的動詞帶過**：「進一步分析」「交叉驗證」「深入調查」這種寫法等於什麼都沒說。讀者想知道你怎麼分析、怎麼驗證的。用一句話說明實際做法，讓讀者能判斷這個驗證方法合不合理
- **解釋差異的成因**：描述兩邊結果不同時，一定要補上造成差異的原因，否則讀者只會覺得「所以呢」
- **只在必要時補背景**：團隊日常使用的工具和概念（如 AFLGo、Docker、CI）不需要解釋，大家都知道。但如果提到某個比較內部、比較 specific 的機制或元件，而不是每個讀者都清楚它的角色，就用一句話（或一個括號）說明它是幹嘛的
- **具體到讀者看得懂為止**：避免「中間的資訊傳遞斷裂導致標記遺失」這種抽象到沒人看得懂的說法。用「做什麼用的」來描述技術概念，但要具體到讀者能理解實際發生了什麼

## 文風注意事項

- 中文一律使用**全形標點符號**（，。、：；「」（）！？）。技術符號、程式碼、檔名、指令參數（如 `--scanner fortify`、`.fpr`）維持原樣，不要把裡面的半形標點轉成全形
- 不要使用「——」（全形破折號），這在中文技術文件中顯得不自然，讀起來像 AI 生成的。改用逗號、句號分隔，或直接拆成獨立的 bullet
- 標題（`h3.`）不要加 ticket 號碼前綴。直接寫 `h3. 標題`，不要寫 `h3. [PDMS-123] 標題`

## Jira Wiki Markup 語法

Jira wiki markup 跟 markdown 不同，以下幾個特別容易搞錯：

- **粗體**：用 `{*}文字{*}`。不是 markdown 的 `**文字**`；也不要用單獨的 `*文字*`，那在 bullet 開頭會被當成 list marker
- **等寬字 / 程式碼**：**只有** `{{文字}}` 這一種。Jira wiki markup **沒有** backtick 語法，用了不會渲染成 monospace，只會原樣顯示反引號字元
- **程式碼區塊**：`{code:語言}` 開頭、`{code}` 結尾。不是 markdown 的三個 backtick
- **純文字區塊**：`{noformat}` 開頭與結尾，適合貼 log、錯誤訊息這類沒有語言的輸出
- **警告文字**：`{color:red}文字{color}`
- **表格**：標題列每一格用兩個直線包住，資料列改用一個直線，而且**不需要** markdown 那條 `---` 分隔線（Jira 也不支援）：

```
||版本||crash 數||CmpLog||
|libaflgo|429|有|
|原版|0|無|
```

檔名、設定值、環境變數、技術名詞都用 `{{...}}` 包起來。適當的格式修飾能讓讀者快速掃讀重點，避免整篇都是同樣樣式的文字。

## 工作流程

### 1. 確認 Jira MCP 可用

先確認 `jira_get_issue` 這類 Jira MCP 工具是否可用（實際呼叫一次是最可靠的判斷方式）。

**如果不可用，停下來告訴使用者，並詢問要怎麼處理，不要自己往下寫。** 原因是：沒有讀到既有 comments 就寫，產出的內容很可能跟前面的 comment 重複、風格不一致、或是接不上前一則的脈絡，這種 comment 貼上去反而要重寫。與其產出一份需要大改的東西，不如先問清楚。

### 2. 取得 Ticket 號碼

使用者必須提供 Jira ticket 號碼，絕對不要自己猜測或推斷。如果使用者沒有提供，直接詢問。

### 3. 讀取該 ticket 的全部 Comments

用 `jira_get_issue` 並帶上 `include: "comments"` 與 `comment_limit: 100`（這是上限值），把該 ticket 的 comments **全部**讀完，不要只看最近幾則。

要讀全部是因為：這張 ticket 的脈絡是累積出來的，只看最後一兩則會漏掉早期定下的名詞、決策、以及已經回答過的問題，導致你重複交代已經寫過的背景，或用了跟前面不一致的稱呼。如果回傳剛好是 100 則，提醒使用者可能還有更早的 comment 沒讀到。

累積久的 ticket 很容易一次回傳好幾萬字，超過工具輸出上限而被存成一個 JSON 檔。遇到這種情況不要改用小的 `comment_limit` 草草了事，那等於又退回只讀最近幾則。改成寫個一次性的小 script 從那個 JSON 抽出每則 comment 的時間與內容再讀，例如：

```bash
python3 -c "
import json,sys
d=json.load(open(sys.argv[1]))
r=d['result'] if isinstance(d,dict) and 'result' in d else d
if isinstance(r,str): r=json.loads(r)
for c in (r.get('comments') or r.get('fields',{}).get('comment',{}).get('comments') or []):
    print('=====', c.get('created'), c.get('author',{}).get('displayName',''))
    print(c.get('body',''))
" <那個 JSON 檔的路徑>
```

讀的時候注意兩件事：

- **抓取風格與詳略程度**：既有 comment 的語氣、結構、寫多細，你的產出要跟它一致
- **無視 MCP 的格式轉譯**：透過 MCP 讀回來的 comment 會被轉成 markdown 的樣子（`h3.` 顯示成 `###`、`{{...}}` 顯示成反引號、`||表格||` 顯示成 markdown 表格）。這是 MCP 抓取時的轉譯，不是使用者原本寫的格式。不要因此誤判使用者是用 markdown 寫 comment，產出時一律使用 Jira wiki markup

### 4. 回顧 Session 內容

回顧這次 session 做了哪些事：討論了什麼問題、實作了什麼、遇到什麼困難、目前狀態如何。

同時盤點**有哪些具體產物可以當證據**：跑出來的數字、實際的錯誤訊息、測試結果、關鍵的設定或指令。這步做得確實，第 5 步才寫得出有份量又不冗長的內容。

### 5. 撰寫 Comment

根據內容的複雜度彈性決定結構。

**簡單任務**（單一問題修復、小調整）：

```
h3. 修復 XXX 問題

* 描述描述，{*}結論是 XXX{*}
* 確認 {{某個設定}} 已正確配置
```

**較複雜的任務**（多個面向、較長的工作過程）：

```
h3. 實現 XXX 功能

一兩句話交代整體概況

h4. 子主題 A
||項目||結果||
|A|123|
|B|456|
差異來自 XXX

h4. 子主題 B
* {*}關鍵發現{*}：描述描述
```

結構不固定，根據內容自然地組織即可。

### 6. 刪一輪

初稿寫完不要直接輸出，一定要再走一次刪減。第一版幾乎必然太長，因為在寫的當下每一句看起來都有道理，要退一步才看得出哪些是重複的。

依序檢查：

1. **表格或程式碼旁邊的散文，有沒有在講同一件事？** 有就刪掉那句。這是目前最常見的問題：證據加上去了，但原本的敘述沒有跟著拿掉，結果比不加還長
2. **有沒有哪個 bullet 是在用文字描述一個本來就有具體形態的東西？** 有就換成表格或輸出片段
3. **有沒有寫進 session 裡沒發生過的東西？** 例如自己補一句「下一步會如何如何」，但使用者根本沒說過。這種話貼上去之後會變成對外的承諾，一定要刪掉
4. **每個段落是不是都在講新的事？** 開頭的概述常常跟後面的小節重複，重複的就合併或刪掉
5. **有沒有哪一段用截圖會比文字更好懂？** 刪減的過程很容易把這件事忘掉。如果有，記得在 codeblock 外面提醒使用者補圖（見上方「截圖」段落）

長度上抓個感覺：單一主題的工作，六到十行就該講完；就算是橫跨多個階段、做了整天的工作，也應該在二十五行內收完。超過這個量體，通常不是工作太複雜，而是還沒刪乾淨。

### 7. 輸出

將最終的 Jira wiki markup 包在 markdown codeblock 中輸出，讓使用者直接複製：

````
```
h3. 標題

* 內容
```
````

codeblock 之後：

- 如果有值得補截圖的地方，用一兩句話提醒（見上方「截圖」段落）
- 簡短提示使用者可以直接複製貼到 Jira

**不要自行發佈 comment。** 不要呼叫 `jira_add_comment`、`jira_edit_comment`，也不要詢問使用者要不要幫忙發佈。使用者會自己檢查、調整後再貼上去，這是他保留的最後一道把關。
